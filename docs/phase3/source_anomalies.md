# Phase 3 — Source Anomalies（來源資料異常紀錄）

> 依規定：本文件記錄的所有異常**均未被自行修正**。`data/rules/*.json` 中對應規則
> 之 `anomaly_flag` 欄位指向本文件對應編號，Rule Engine 使用者可自行決定如何
> 處理。凡涉及數值判斷之異常，Rule Engine 之實作採「保留原文標籤、以推定數值
> 運作、但明確標記」之最小侵入策略，絕不悄悄視為已解決。

## ANOMALY-01：站牌之接近程度或密集程度 — m/km 誤植

**位置**：評價基準明細表範例.pdf（區域因素）頁2，「站牌之接近程度或密集程度」列，
「普通」級距。

**原文**：`普通： 200km以上未滿400m`

**問題**：與同一因素之其餘級距比對（優=區段內有，稍優=未滿200m，稍劣=400m以上
未滿700m，劣=700m以上），「普通」級距之下界應與「稍優」上界（200m）銜接、上界
應與「稍劣」下界（400m）銜接，故「200km」在單位與數量級上均與上下文不連續，
高度疑似「km」為「m」之誤植。

**處理方式**：`data/rules/regional_rules.json` 中對應規則（`REG-BUS_STOP_PROXIMITY-03`）
之 `grade_label` 保留原文完整字串（含「200km」字樣及本異常註記），但
`lower_bound`/`upper_bound` 欄位為使 Rule Engine 可運作，採用**推定之 200/400（單位M）**
數值。`anomaly_flag` 欄位明確指向本編號。若決賽發現官方基準表對此因素有不同數字，
須以官方決賽當次資料為準，不得逕用本推定值。

**信心等級**：高（上下文連續性極強，合理懷疑為誤植）；但未達到「確定」等級，
故不視為官方確認之訂正。

## ANOMALY-02：接近觀光遊憩設施之程度 — m/km 誤植

**位置**：評價基準明細表範例.pdf（區域因素）頁3，「接近觀光遊憩設施之程度」列，
「稍劣」級距。

**原文**：`稍劣： 1,000km以上未滿1,500m`

**問題**：與 ANOMALY-01 相同性質。上下文（普通=500m以上未滿1,000m，劣=1,500m
以上或無）顯示「稍劣」應銜接於1,000m至1,500m之間，「1,000km」疑為「1,000m」
之誤植。

**處理方式**：同 ANOMALY-01，規則 `REG-TOURISM_FACILITY_PROXIMITY-04` 之
`grade_label` 保留原文，`lower_bound`/`upper_bound` 採推定值（1000/1500，單位M），
`anomaly_flag` 指向本編號。

**信心等級**：高（同上）。

## ANOMALY-03：宗地深度 — 非單調（U型）分級結構

**位置**：評價基準明細表範例.pdf（個別因素）頁6，「深度」列，「劣」級距。

**原文**：`劣： 未滿10m或100m以上`

**問題**：這不是傳統文字/單位錯誤，而是一種**結構性異常**——深度因素之「劣」級距
同時涵蓋「過小」（未滿10m）與「過大」（100m以上）兩種情形，屬非單調（U型）分級，
與本表其餘所有數值型因素之單調遞增/遞減級距結構不同（其餘因素皆為「值越大越好」
或「值越小越好」之單一方向）。

**處理方式**：本階段**未**在 Rule Engine 中特別實作雙區間（U型）比對邏輯——
`data/rules/individual_rules.json` 中 `IND-LAND_DEPTH-05`（劣）之
`lower_bound=None, upper_bound=10`，僅涵蓋「未滿10m」之情形，**未涵蓋「100m以上」
之情形**。若實際輸入深度為150m（例如），目前 Rule Engine 將對此因素拋出
`RuleNotFoundError`（因未落入優/稍優/普通/稍劣任一區間，也未落入劣之10以下區間），
而非正確判定為「劣」。此為**已知限制**，非靜默錯誤——Rule Engine 選擇「找不到規則
就報錯」而非「猜測」，符合本專案deterministic原則，但表示深度因素之規則定義本身
尚不完整，需於後續版本擴充雙區間支援（例如將 `upper_bound` 欄位擴充為可選的
`secondary_lower_bound`/`secondary_upper_bound`，或改用區間清單而非單一上下界）。

**信心等級**：高（原文清楚，屬結構性設計問題而非誤植，故不宜比照ANOMALY-01/02
逕自推定合併）。

## ANOMALY-04：交流道之有無及接近交流道之程度 — Golden Case「無」與最劣等級的對應

**位置**：查估書表範本.pdf 表1（頁1），交流道列：「名稱：無交流道 ○本區段內
○本區段外(距 M)」（距離欄空白）；表5-2（頁2）「交流道之有無及接近交流道之程度」
記載為 `5 劣`。

**問題**：表1中交流道之距離欄位**空白**（既非本區段內，亦未填寫本區段外之距離
數字），但表5-2逕行判定為「劣」（最差等級）。作業手冊填表說明（p.29）僅說明
「填寫該地價區段鄰近之交流道(匝道)名稱...並按本區段中心點至該交流道之距離填寫」，
未明確規範「無此設施時」是否應自動判定為最劣等級，或應視為「距離無限遠→優」
（因交流道通常屬「越遠越安靜」或「越近越便利」，需視個別評價基準明細表之
direction而定，此因素為distance_positive，即越近越優，因此無交流道理論上應視為
「距離為∞」而應判優，但Golden Case卻記載為劣）。

**團隊觀察（非官方確認）**：金山區範例將「無交流道」對應至「劣」，可能反映
「大型交通建設的『無』本身對某些用地類型是負面因素（缺乏交通建設可及性）」之
在地判斷，而非「越近越優」邏輯之機械套用。此為評價基準明細表可能存在之在地
特殊判斷，Sources未見明文說明其理由。

**處理方式**：`data/rules/regional_rules.json` 未新增「無此設施」之特殊規則，
Rule Engine 目前要求呼叫端明確提供一個數值或標籤（不支援直接傳入「無」）。若
決賽案例出現「無此設施」情形，系統設計上應由 Data Acquisition Layer 依個案之
評價基準明細表明文對照，不得由 Rule Engine 自動假設「無=劣」或「無=優」。

**信心等級**：中（現象明確，但成因與是否為普遍規則未經官方確認）。

## ANOMALY-05：區域因素矩陣行列方向未能由 Golden Case 獨立驗證

**位置**：評價基準明細表範例.pdf（區域因素）頁1-5，全部27個修正率矩陣。

**問題**：本階段已用 Golden Case **個別因素**（表4）之5個非平凡案例（比準地與
比較標的等級不同）獨立驗證矩陣方向為「列=比準地等級，欄=比較標的等級」（見
`rule_engine_spec.md`）。然而，Golden Case中比準地與比較標的1**同屬地價區段
P002-00**，導致**全部27項區域因素**之比準地與比較標的等級恆相同，修正百分比
恆為0.00%（退化情形），無法用來獨立驗證區域因素矩陣本身的行列方向。

**處理方式**：`data/rules/regional_rules.json` 之矩陣方向設計**依類比**沿用
個別因素表已驗證之方向（兩份表格採用完全相同的表頭文字樣式「比凖地(比較標的)」
／「宗地(比準地)」，見 `rule_engine_spec.md` 詳細論證），但此僅為**類推**，非
**獨立驗證**。若決賽案例之比準地與比較標的分屬不同地價區段（產生非零區域因素
修正百分比），**強烈建議**於取得決賽評價基準明細表後，優先用該案例之非平凡
區域因素數據重新驗證矩陣方向，再進入正式計算，避免此假設若有誤而系統性影響
所有區域因素修正率的正負號。

**信心等級**：中（類推理由充分，但終究未經獨立數值驗證）。

## ANOMALY-06：個別因素與區域因素之建蔽率/容積率級距數值不同

**位置**：評價基準明細表範例.pdf 頁1（區域因素建蔽率/容積率）vs 頁8-9（個別因素
建蔽率/容積率）。

**問題**：
- 區域因素建蔽率：優=60%以上；個別因素建蔽率：優=80%以上。
- 區域因素容積率：優=240%以上；個別因素容積率：優=300%以上。

兩份表格對「同名」因素（建蔽率、容積率）採用**不同的級距門檻**。這並非錯誤
（區域因素評的是整個地價區段的普遍水準，個別因素評的是特定宗地相對於其他宗地
的優劣，兩者評價目的不同，門�踏不同屬合理設計），但**極易造成系統實作或人工
審查時的混淆**，例如誤將表5-2之建蔽率修正率直接套用於表4，或反之。

**處理方式**：`schemas/rule_schema.json` 之 `category` 欄位（如「土地使用管制(1)」
vs「行政條件(5)」）與 `rule_id` 前綴（`REG-` vs `IND-`）已足以在資料層面區分兩者，
不會混用；本異常僅為提醒性質，供 Phase 4 開發介面時特別注意欄位分組之UI標示。

**信心等級**：高（現象直接可見，非臆測）。

可自行決定是否於下次維護 Phase 2 文件時一併修正該三處文字敘述（非資料本身）。

## ANOMALY-09（Rule Engine開發過程中發現並已修復之邏輯缺陷，非Source異常，記錄供追溯）

**位置**：`engine/rule_engine.py` 開發過程，pytest首次執行時發現。

**問題**：凡「優」等級定義為「區段內有」（無數值界限，非距離）之因素（如
停車場地之便利程度、市場、公園、觀光遊憩設施、百貨公司、金融機構、娛樂設施、
大型展示中心或觀光飯店等8項regional因素），因其 `lower_bound`/`upper_bound`
均為 `None`，原始 `_match_numeric()` 實作對「上下界皆為None」預設視為「無條件
通過」，導致任何數值輸入（包括Golden Case真實案例120M）都會優先誤判為「優」。

**發現方式**：`tests/test_golden_case.py` 之
`TestGoldenCaseRegionalGradeBands::test_regional_grade[停車場地之便利程度-120-M-2]`
測試失敗（實際66筆測試中1筆失敗），錯誤訊息顯示 grade_code 應為2（稍優）卻得到1
（優）。

**修復方式**：`_match_numeric()` 新增邏輯：上下界皆為None之候選規則視為
「類別型哨兵狀態」，於數值比對時直接跳過，僅能透過傳入該狀態對應之文字標籤
（如「區段內有」）明確匹配；同時調整單位檢查邏輯，使其僅套用於真正的數值輸入，
不對文字標籤輸入強制要求單位。修復後新增3筆專門測試（`TestWithinSegmentSentinel`）
鎖定此行為，pytest全數69筆測試通過。

**信心等級**：高（可由 `tests/` 測試結果直接覆核，修復前後之diff已保留於本次
對話紀錄）。此為工程實作缺陷之記錄，不屬於「Source資料異常」範疇，但依專案
「不得隱藏Known Limitation或失敗」原則一併如實記錄。
