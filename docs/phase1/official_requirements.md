# Phase 1 — 官方需求與競賽規格基線

> 本文件為 Sources 之綜整摘要。每項結論之詳細出處、時間戳與分類請參閱
> `evidence_matrix.md`（本文件內以 `[REQ-xxx]` 標註對應列）。凡未標註分類者，
> 預設為【官方明確要求】；標註【官方建議】【講者舉例】【合理推論】【團隊建議】
> 【待確認】者以方括號註明。

## 1. 官方題目

「AI 輔助不動產估價案件審查」——新北市政府地政局組競賽題目。`[REQ-001]`

## 2. 背景

不動產估價案件審查時，審查人員須依估價師填具之估價書表，逐一檢核是否依「評價因素
基準明細表」正確判定優劣等級及修正率，涵蓋區域因素（如接近聚落、市場、嫌惡設施等）
及個別因素（如面積、形狀、道路條件等）。`[REQ-001]`

## 3. 痛點（官方原文列點，非團隊歸納）

1. 估價書表涉及表單眾多，人工逐項比對耗時且易發生疏漏。
2. 區域因素與個別因素需依不同用地類別基準明細表判定，人工判讀一致性不易維持。
3. 修正率加總及跨表抄填（如區域因素總修正數）容易出現計算或填載錯誤。`[REQ-001]`

工作坊現場並補充說明：機關審查人員須人工比對表1、表5-2、表4三張表單，逐項核對
距離、級距、修正率及加總結果，作業時間長，且易因人工判讀或抄填錯誤影響審查品質。
`[REQ-001, REQ-023]`

## 4. 預期成果及效益

1. 透過 AI 輔助完成估價書填寫流程。
2. 降低人工審查時間與錯誤率，提升估價審查效率與一致性。
3. 作為未來推動估價審查數位化與智慧化之基礎應用案例。`[REQ-002]`

## 5. 競賽輸入（Confirmed / Likely / Unknown 摘要，詳見 `competition_io_spec.md`）

- **賽前提供**：實際查估書表範本（金山區 Golden Case）＋土地徵收補償市價查估作業
  手冊＋區域因素／個別因素評價基準明細表範例（金山區商業用地）。`[REQ-003]`
- **參賽者可自行取用**：政府既有公開統計網站之公開資料，不限於官方提供之資料集。
  `[REQ-003]`
- **決賽現場提供**：一份查估書表（區段編號／區段範圍已預填，其餘欄位空白）＋對應
  該區段之區域因素／個別因素評價基準明細表。區段（案例）與賽前範例**不同**，用地
  類別**不一定**為商業用地。`[REQ-006, REQ-007]`
- 官方**不會**額外提供地籍圖、都市計畫使用分區圖等 GIS 圖層原始檔；此屬「延伸應用」
  範疇，須自行運用公開資料設計。`[REQ-005]`
- 官方**不會**提供其他行政區或其他用地類別之額外評價基準明細表作為賽前參考——
  金山區商業用地範例是賽前唯一提供的基準表範例。`[REQ-006]`

## 6. 地政局組額外需完成的估價書表任務

- 填寫完成三張核心書表：表1地價區段勘查表、表5-2影響地價區域因素分析明細表、
  表4比較法調查估價表。此為官方口頭確認「一定要看到的基本」。`[REQ-004]`
- 每次查估以單一標的（單一比準地／單一區段案例）為原則，非多標的同時估價。
  `[REQ-008]`
- 地價區段圖／略圖／使用分區套繪圖等圖籍非必填，但若能延伸產製或說明，屬加分項目。
  `[REQ-005]`

## 7. 最終 Output（可確認項目）

1. 填寫完成之查估書表 PDF（表1、表5-2、表4）——最基本、必要之解答內容。
   `[REQ-004, REQ-009]`
2. 介紹簡報（5-6分鐘，時間含Live Demo／影片播放）。`[REQ-013, REQ-014]`
3. 部署於 AWS 正式競賽環境之 Live Demo 連結（非本機執行）。`[REQ-013, REQ-015]`
4. 錄製之操作過程影片，展示AI如何協助完成填寫流程。`[REQ-013]`
5. 依錄取通知信，決賽提案內容另須包含：命題連結、數據及資料應用、技術架構、
   生成式AI技術應用說明；最終交付清單以9/12決賽現場公告為主
   【待確認：現場是否會調整或增列項目】。`[REQ-017, REQ-019]`

## 8. 填寫完成的估價書表在競賽中的角色

填寫完成的三張書表是評分「第一關最基本的要求」（填答正確性），同時也是評分委員
用以檢視「填答過程邏輯」與「AI輔助運用程度」的具體載體——即書表本身既是答案，
也是評分委員追溯系統運作邏輯是否正確、是否只是套版硬記的依據。`[REQ-012]`

## 9. Live Demo / AWS 相關官方要求

- Live Demo 必須部署在雲端（AWS）環境，不可在本機或跳板機執行；目的是確保評審能
  實際進入系統操作，而非僅觀看預錄影片或靜態簡報。`[REQ-013]`
- 正式參賽作品須使用「正式比賽的AWS環境」，賽前僅能研究準備，無法把系統於賽前
  完整建置好後直接在決賽當天沿用（暗示決賽現場另有指定的AWS環境或帳號機制）。
  【待確認：具體提供方式，例如是否為新開AWS帳號、Bedrock額度上限、是否延用工作坊
  帳號等技術細節】`[REQ-015]`
- 僅限使用 AWS 服務提供之基礎模型（Foundation Model）——即生成式AI能力須透過
  Amazon Bedrock 等 AWS 原生管道取得，不可直接串接非AWS供應之外部LLM API。
  `[REQ-016]`
- 簡報時間 5-6 分鐘／隊，形式不限（純簡報／Live Demo／預錄影片+旁白皆可），惟
  所有形式切換與轉場時間均計入該時段，不另外延長。`[REQ-014]`

## 10. 評分重點（僅列 Sources 有支持之方向；無官方公開權重百分比）

1. **填答正確性**——官方原話：「第一關最基本的要求」。`[REQ-012]`
2. **整套填答過程的邏輯**，以及運用AI輔助查估作業的程度與方式（資料整理、分析
   計算、檢核），用以評估團隊「運用AI實際應用的能力」。`[REQ-012]`
3. **自動化程度／精準度／流程易用性**：越接近全自動化（匯入空白書表→直接產出
   填寫完成書表）且保有準確率者，越符合業務需求、越容易得高分；仰賴人工匯出
   Excel再手填的流程屬可接受但非最優。`[REQ-009]`
4. **延伸應用**（鼓勵但非必做）：如AI輔助產製圖籍、建立估價報告書智慧檢核機制
   （自動比對表單內容、檢查級距對應與修正率是否正確一致、找出填載或計算錯誤），
   以及其他「落地式AI應用創新手法」，官方表示「都會納入這次的評分考量」。
   `[REQ-005, REQ-012]`
5. 官方全程未於工作坊中提供任何評分項目的數字化權重／百分比配分；
   `evaluation_focus.md` 依規定不得自行杜撰配分比例。`[REQ-012]`

## 11. 官方限制（Strict Constraints）

- 僅限使用 AWS 服務提供之基礎模型。`[REQ-016]`
- Live Demo 必須實際部署於雲端，可被評審獨立進入操作驗證。`[REQ-013]`
- 決賽競賽案例的區段範圍、可能的用地類別皆與賽前範例不同，系統設計不可
  Hardcode 金山區 P002-00 案例；官方原話：「這套系統是不可能是只針對單一區段
  去做這個輔助填答的」。`[REQ-006]`
- 官方不提供 GIS 圖層原始檔，僅提供PDF形式之參考資料；圖資延伸需求須仰賴
  參賽者自行取用公開資料。`[REQ-005]`
- 決賽全員須9/12-13全程參與（含開幕、競賽實作、評審簡報、頒獎典禮）方可取得
  完賽證明；此為行政面而非系統設計面之限制，記錄供團隊留意。`[REQ-017, REQ-018]`

## 12. 特別提醒：距離量測規則（官方兩次口頭覆述，屬考前提示）

- 一般設施（交通運輸、公共建設等）之接近程度／距離量測，原則採**最近距離**
  （第二次覆述時用語為「最近的步行距離」）。`[REQ-010]`
- 特殊設施（如殯葬設施）之距離量測，採**直線距離**。`[REQ-010]`
- 官方表示此規則於作業手冊中亦有相關內容可供對照，但團隊尚未在手冊中定位到
  與此「一般設施 vs 特殊設施」二分法逐字對應的段落；請參閱
  `open_questions.md` 中對應項目。`[REQ-010]`

## 13. 三表聯動關係（官方口頭提醒，直接支持 Core 專案的 Cross-Form 設計）

表1（地價區段勘查表）→ 表5-2（影響地價區域因素分析明細表）→ 表4（比較法調查
估價表）之間具資料聯動：表5-2 的優劣等級資料須與表1 之區勘結果一致；表5-2 之
「影響地價區域因素總修正數」須等同表4 之「區域因素調整百分率」；任一上游欄位
錯誤將導致下游「聯動錯誤」。此聯動關係與作業手冊中官方既有審查checklist高度
重疊（見第14節）。`[REQ-011, REQ-023]`

## 14. 官方既有人工審查 SOP（作業手冊，可作為 Smart Review 規則設計之直接依據）

直轄市/縣（市）主管機關提交地評會前之審查重點包含：`[REQ-023]`

- 確認地價區段勘查表之區段範圍描述與現況相符，各細項優劣等級是否依評價基準
  明細表填列。
- 確認影響地價區域因素分析明細表之修正細項優劣等級與地價區段勘查表所載內容
  一致；修正百分比是否依基準明細表調整。
- 確認比較法調查估價表之交易日期與買賣實例調查表一致；區域因素調整百分率與
  影響地價區域因素分析明細表之總修正數相符；個別因素調整之差異率依基準明細表
  填列；各比較標的之權重是否符合邏輯。

此為官方（內政部）既有制度化審查流程，早於本次黑客松存在，可視為 Core B（AI輔助
智慧審查）之官方業務基礎，惟其本身屬「既有制度」而非「本次競賽新增要求」，故本節
分類為【官方明確要求】限於「此SOP確實存在且為官方審查依據」，而非「competition 要求
參賽者100%重建此SOP的全部檢查項」——後者為【合理推論】，因命題文件與工作坊皆聚焦於
表1/表5-2/表4三表，未明確要求連動至表7/8/9/13/14等後續書表。

## 15. 尾數計算與計算精度規則（作業手冊，官方明確要求）

- 比準地地價／宗地市價尾數：依金額級距分段無條件進位（≤100元進位至個位、
  100~1000元進位至十位、1000~10萬元進位至百位、逾10萬元進位至千位）；市價
  變動幅度二次調整後，統一無條件進位至個位數以避免重複進位。`[REQ-021]`
- 表4「比準地比較價格」（試算價格之加權結果）尾數，採**四捨五入**至個位數——
  與上述「無條件進位」規則不同，Calculation Engine 不可混用。`[REQ-022]`
- 上述規則與既有團隊發現「中間值需保留完整精度、僅於最終輸出四捨五入」的方向
  一致，且官方文字明確區分了「地價本身尾數」（無條件進位）與「比較價格尾數」
  （四捨五入）兩種不同規則，此區分為本階段新增之關鍵發現。
