# Phase 1 — Open Questions

依 Prompt 要求分為四類：資料矛盾／未說清楚／需要決賽前確認／需要技術假設。
每題附優先度（P0=決賽前必須確認、P1=強烈建議確認、P2=可暫時擱置以假設代替）。

## A. 資料矛盾（逐字稿 / 畫面 / 文件間之衝突）

### A-1（低優先，不影響系統設計）
逐字稿中「地政局」被系統性誤植為「地震局」（如 [00:11:08-00:11:10]），「查估」被
誤植為「茶菇」（如 [00:12:27-00:12:31]）等。此為 ASR（語音辨識）系統性錯字，非
內容矛盾。**證據可靠性判斷**：已抽樣視覺比對關鍵畫面（frame 18，00:12:44），畫面
中 Microsoft Teams 參與者列表清楚顯示「地政局解題...」字樣，證實正確用詞為「地政
局」，逐字稿為誤植。依規定不得「偷偷修正」，故本階段所有文件在首次引用逐字稿時均
保留原字並於此註明。

**結論**：非真正的資料矛盾，而是單一資料源（逐字稿）本身的已知瑕疵，已用視覺畫面
驗證更可靠的一方。優先度：無需決賽前確認，僅供後續文件撰寫時參考。

### A-2（中優先）
關於「距離量測規則」，工作坊口頭提醒的分類方式是「一般設施（最近距離）vs 特殊設施
（直線距離）」（`evidence_matrix.md` REQ-010），但團隊先前針對 Golden Case 數值
比對所發現的規律，是「區域因素距離量測以地價區段中心點為量測起點，個別因素距離
量測以宗地實際位置為量測起點」（詳見下方【本輪修正】之精確數值說明）。
這兩套分類邏輯（設施類型 vs 量測起點）**並非互斥，但也非等價**，Sources 中未見
官方將兩者明確關聯或統一說明。

**【本輪修正，原描述「兩者恰好皆為80M」不精確，已於NO-GO Recovery中依原始查估書表範本
重新核對數值】**：Golden Case 金山第一公墓案例，原始查估書表範本實際記載三個不同數值：
表1地價區段勘查表（區段層級，P002-00）記載距金山第1公墓80M；表4比較法調查估價表
個別因素欄位中，比準地一列記載距金山第一公墓260M，比較標的1一列記載距金山第一
公墓80M。三者並非全數相同——巧合相等僅發生於「表1區段層級之80M」與「表4比較標的1
個別因素之80M」之間，比準地本身之個別因素距離（260M）與前二者並不相等。

**結論**：屬「未說清楚」而非直接矛盾，因兩套規則可能同時存在（分別回答「用哪一種
演算法量」與「以哪個座標點為起點量」兩個不同問題）。**待確認**：官方所稱「特殊設施
用直線距離」，其量測起點是否仍依「地價區段中心點 vs 宗地實際位置」的區分？作業手冊
全文中尚未定位到與「一般設施/特殊設施」逐字對應之明確段落。優先度：P1。

## B. 未說清楚（Sources 內容不完整或過於簡略，須合理假設暫代）

### B-1
官方提及「其他影響因素」欄位之填寫「應先看評價基準明細表是什麼然後去做對應的
填寫」（`evidence_matrix.md` REQ-020），但未具體展開「其他影響因素」實際涵蓋哪些
子項目、如何轉換為百分比。作業手冊本身對「其他影響因素」之填表細節亦僅為概略性
文字（「按該地價區段用地使用性質足以影響其區段地價之因素，對於地價影響之程度」），
無固定公式。**優先度：P1**——建議決賽拿到當次評價基準明細表後，第一時間檢查其
「其他影響因素」欄位定義是否比金山範例更明確。

### B-2（【2026-09-01更新：已透過母法規查證解決，見REQ-029】）
表4「比較標的權重」決定公式，官方僅以「調整百分率絕對值加總 7%/10%/15% 對應
較高/普通/較低，權重50%/30%/20%」為**舉例**（作業手冊 p.52-53 原文「舉例而言」），
且明確使用「舉例」二字，非固定公式；當僅有1筆比較標的時，官方明文權重=100%。

**已解決**：直接向 law.moj.gov.tw 查證作業手冊比較法規定所依據之母法規《不動產
估價技術規則》第27條全文，確認**母法規本身同樣沒有精確映射函數**——第27條僅
規定「考量各比較標的蒐集資料可信度、各比較標的與勘估標的價格形成因素之相近
程度，決定勘估標的之比較價格」，沒有任何數學公式（無論線性內插、固定級距對照
表皆無）。這代表「2筆以上比較標的時精確權重怎麼算」不是Sources缺口，而是**母
法規本身即刻意留給估價師專業判斷**，非團隊能力所及可查出更精確答案。

**衍生發現**：查證過程中同時確認第27條明文要求「三件以上」比較標的，而非原本
推測的「2件以上」，已於 evidence_matrix.md REQ-029 更正。

**系統設計因應**：`engine/comparable_selection_engine.py` 之 `suggest_weights()`
實作一個**明確標示為系統建議、非法規規定**的權重演算法（反比於調整率絕對值加總），
`SuggestedWeight.requires_human_confirmation` 恆為 `True`，絕不冒充為官方公式。

### B-5（新增，2026-09-02，使用者對§25 30%門檻實作提出質疑後二次查證發現）

不動產估價技術規則§25原文：「...任一單獨項目之價格調整率大於百分之十五，或
情況、價格日期、區域因素及個別因素調整**總調整率**大於百分之三十時...應排除
該比較標的之適用」。條文本身未定義「總調整率」之精確計算公式（是否為情況+
價格日期+區域+個別因素「先加總後取絕對值」，或「各項先取絕對值後加總」）。

**已重新查證但未能解決**：直接查對law.moj.gov.tw §25全文（無公式）、以及
土地徵收補償市價查估作業手冊表4「比較法調查估價表」段落p.52-53之「（十）
調整百分率絕對值加總請依各比較標的，各項調整百分率先取絕對值後加總計算之」
——此為手冊中唯一之「絕對值加總」明文公式，但緊接的「（十一）」段落明確將
其用途限定於§27權重判斷（「『調整百分率絕對值加總』可作為『價格形成因素之
相近程度』之衡量判斷」），並未提及§25排除門檻。手冊全文查無「總調整率」於
§25語境下之定義。

**此前之實作錯誤**：`ComparableSelectionEngine.check_exclusion()`最初將§25之
「總調整率」直接假設等於「先加總後取絕對值」，並據以自動判定`excluded=True`。
此為團隊自行發明公式並冒充官方規則之錯誤，已修正。

**系統設計因應**：`check_exclusion()`現在計算兩種候選讀法
（`total_adjustment_signed_sum_pct`／`total_adjustment_abs_component_sum_pct`）
並列供估價師參考，`total_adjustment_legal_basis`固定標示`"LEGAL_BASIS_
UNCONFIRMED"`；`excluded`欄位僅依§25明文清楚之15%單項門檻決定，30%總門檻
不再驅動任何自動排除，但兩讀法之一旦超過30%仍會使該欄位狀態變為
`MANUAL_REVIEW_REQUIRED`，提示估價師人工判斷。**優先度：P1**——建議決賽前
若有機會向主辦方確認§25「總調整率」之官方計算方式。

### B-3
逐字稿中「地政局地下科長」（原文誤植，`evidence_matrix.md` REQ-028）之完整職稱、
以及「業務單位」與「地政局代表」是否為同一人或不同單位代表，Sources 無法完全
釐清。**優先度：P2**，不影響系統設計，僅供之後正式引用發言人身分時參考。

### B-4（新增，NO-GO Recovery BLK-01 根因分析所發現）
表4「調整至估價基準日單價」欄位（Golden Case中為188,459，由比較標的土地正常單價
184,763經價格日期調整率約2%換算而來）之尾數進位規則，Sources 全文未見明文規範。
作業手冊已知之兩項尾數規則——REQ-021（比準地/宗地地價本身，分級無條件進位）與
REQ-022（比準地比較價格最終欄位，四捨五入）——經逐字核對條文主詞，均不涵蓋此一
中間欄位。且重新試算184,763×1.02=188,458.26，依一般四捨五入應得188,458，與Golden
Case表單實際顯示之188,459有1單位差異，差異原因無法由現有Sources解釋（可能為官方
範例製作時之筆誤、或存在未公開之進位規則、或價格日期調整率並非精確之2%整數而是
另有精確係數）。

**結論**：屬 Sources 真實缺口，非團隊得自行假設補齊之業務規則。**優先度：P1**——
建議決賽取得評價基準明細表後，若時間允許可嘗試向主辦方確認此欄位進位規則；若無法
確認，Calculation Engine 應暫採「保留完整精度、不在此中間步驟進行任何形式之四捨五入
或無條件進位，僅於REQ-021/REQ-022明文規範之最終欄位進行對應進位」之安全 Fallback
（對應 `D` 節技術假設 D-6），並在系統輸出中以【待確認】標註此步驟之進位邏輯尚待官方
確認，不得逕自判定何者為「正確答案」。

## D. 需要技術假設（Sources 無法確認，但系統開發必須先有暫定立場才能推進）

以下項目一律以 Placeholder／Config／Mock 型態實作，並在程式與文件中明確標註為
「團隊假設」，不得寫成正式業務規則：

1. **Grade/Adjustment 判定引擎的分級數**：暫時支援金山範例之5級制（優/稍優/普通/
   稍劣/劣），但 Schema 須保留可擴充至2/3/7/9級之彈性（依 REQ-024 官方明文5種
   分級制度）。
2. **多比較標的權重公式**：在官方未提供明確公式前，暫以「調整百分率絕對值加總」
   之相對排序作為權重分配的參考依據（絕對值加總越小、權重越高），並保留人工
   覆核／覆寫的介面，不強制自動決定最終權重數字。
3. **GIS/Distance Engine 的資料來源**：假設決賽不提供GIS圖層原始檔，Provider
   須設計為可切換之 Adapter（可接公開Open Data、可接手動輸入座標、可接Mock
   資料），並在資料缺漏時回傳 `UNKNOWN` 或 `MANUAL_REVIEW_REQUIRED`，不得由AI
   臆測距離數值。
4. **AWS部署環境細節**：暫以團隊自有AWS帳號進行開發與測試，待官方公布正式競賽
   環境規則後再行遷移或調整部署腳本；不假設帳號權限、地區（Region）或模型可用性。
5. **表7以後之書表（徵收土地宗地市價估計表等）**：假設本次競賽範圍**不**要求
   填寫，僅聚焦表1、表5-2、表4三表（依 REQ-004「一定要看到的基本」僅列此三表），
   但保留未來擴充之可能性（見 `official_requirements.md` 第14節之分類說明）。
6. **表4「調整至估價基準日單價」中間欄位之進位規則**（見 `B-4`）：在官方確認前，
   Calculation Engine 暫不對此中間值進行任何四捨五入或無條件進位，全程保留完整
   精度，僅於 REQ-021（比準地/宗地地價本身）與 REQ-022（比準地比較價格最終欄位）
   明文規範之欄位套用對應進位規則；系統應將此步驟標註為【待確認：進位規則】，
   不得自行判定188,458與188,459何者為準。
